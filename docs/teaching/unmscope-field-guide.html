UNMScope Field Guide

UNMScope is the Python replacement for LouisXIV, the LabVIEW program that has run this microscope for years. It is written as a port, not a rewrite: the LabVIEW source stays the authority on what every number means, and the Python has to reproduce it. This page is how the code is laid out and how a feature gets from one to the other.

Where things live

Three sibling trees, one direction of travel

Everything sits under H:\UNM_Lightsheet\ as three folders that never nest inside one another. Information flows left to right and never back: nothing in Python writes into the LabVIEW tree.

reference  →  readable form  →  the port

Authority UNMScope_Source\

The real LouisXIV LabVIEW project — thousands of .vi files, the compiled FPGA bitfile the card actually runs, and SPIMProject.ini with this rig's calibrations. Read-only, and still the software the lab uses.

Readable form VI_Diagrams\

Every VI's block diagram and front panel exported to PNG, mirroring the source tree. This is how the logic gets read without opening LabVIEW — including hidden frames, which expose every case of a case structure and every button's event handler.

The port UNMScope_Python\

The Python package, its tests, the hardware verification scripts, and the docs that record which VI each piece of Python came from. This is the only tree that changes.

Teaching point: a student can read the entire instrument's logic from the PNG exports without a LabVIEW license. That indirection is what made the port tractable.

The pattern that matters most

Every device has a stand-in

This is the single design decision worth explaining first. Each piece of hardware is defined as an abstract interface, and then implemented twice — once against the real driver, once as a simulation. The GUI is written against the interface, so it cannot tell them apart.

Three consequences worth spelling out for students: the whole test suite runs on a laptop with no microscope attached; a bug can be reproduced without booking instrument time; and there is a genuine simulate-on-FPGA mode — simulated camera, real card, analog outputs clamped to zero — for testing timing against hardware without moving a single galvo.

Method

How one feature gets ported

The same seven steps every time. The rule underneath them is that LabVIEW is the reference: if LouisXIV already computes something, the job is to read what it computes, not to re-derive it from physics. That rule exists because re-deriving it went wrong once — a deskew shift direction was inferred from geometry instead of read from the VI, and it was wrong.

  1. Find the VI and read its diagram

    Locate the feature in VI_Diagrams\, including hidden case frames when the logic hides inside a case structure or an event handler.

  2. Transcribe the math verbatim

    Port the formula as the VI computes it, wiring node by wiring node, with a comment naming the VI it came from. Unit conversions and rounding modes included — LabVIEW rounds half-to-even.

  3. Measure the panel, don't eyeball it

    Widget geometry comes from pixel-scanning the rendered LabVIEW panel with PIL, then placing Qt widgets at the measured coordinates. Layouts are checked with a reference-versus-ours delta table.

  4. Wire it to the interface, not the driver

    The panel talks to the abstract device, so it works against the simulation from the first run.

  5. Test against the fakes

    Unit tests for the math, offscreen-Qt tests for the panel. These run in about 35 seconds and gate every commit.

  6. Verify on the real card

    A numbered script in spikes/ drives the actual hardware and, where it matters, the result is confirmed on an oscilloscope or a multimeter at the breakout box.

  7. Write down what was measured

    A file in docs/ records the VI-to-Python mapping, the measured layout table, and explicitly which details are still assumed rather than verified.

Working agreements

Four rules that shape every commit

These live in CLAUDE.md and are the part most worth repeating to a new student.

LabVIEW is the reference.
Port what the VI computes. Do not re-derive it, do not auto-detect it, do not improve it before it matches.
Never claim a layout from looking at a screenshot.
Downscaled images have produced wrong answers repeatedly here. Measure with pixel sampling and publish the delta table.
Unwired controls stay visibly greyed.
A control that looks functional but does nothing is worse than a missing one. Honesty about what is real is a design rule, not a nicety.
The port is a cleanup, not a copy.
LouisXIV accumulated two decades of unused controls. Match what is worth keeping; drop the rest deliberately, and record the decision so it does not creep back.

Running it

From a clean machine

A rig that drives the microscope needs the free NI-RIO driver and Hamamatsu's DCAM — but not LabVIEW, which is only needed to compile the FPGA bitfile in the first place. A laptop needs neither: the simulated backends and the full test suite run on any Python 3.11.

pip install -e ".[dev]" Installs the package and its test tooling.
python -m unmscope.gui Launches the window. Pick Simulated to run with no instrument.
python -m pytest tests -q All 246 tests, about 35 seconds, no hardware required.

Instrument constants a student will meet early: the FPGA counts time in 25 ns ticks (40 MHz); analog channels are ±10 V over 16 bits, or 3276.7 counts per volt; the camera trigger on DIO4 was measured at 100.000 ms; the Orca's 6.5 µm pixels at 30× give 0.2167 µm at the sample; and stacks are acquired with the stage at 45°, which is why they need deskewing.
