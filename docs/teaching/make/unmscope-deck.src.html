Before anything else

A program is just text files in folders

There is nothing hidden or compiled here. Every part of this software is a plain text file you can open in Notepad. The folder names and file names are the organisation — there is no database, no project file that secretly ties it together.

So learning your way around is exactly like learning your way around someone's filing cabinet. Once you know what each drawer is for, you can find anything.

Two words worth knowing, because they appear everywhere:

A "module" is one file

One .py file holding related code. camera.py is the camera module. When someone says "it's in the camera module", they mean open that file.

A "package" is one folder of them

A folder of modules that ships and installs as a unit. Ours is called unmscope. Everything the program needs to run lives inside it.

The widest view

Three folders side by side

All under H:\UNM_Lightsheet\. They are deliberately siblings — none is inside another — so it is always obvious which world a file belongs to.

the original

UNMScope_Source\

The LabVIEW program that runs the microscope today, plus this rig's calibration file. We read from it constantly and never write to it.

a readable copy

VI_Diagrams\

A picture of every page of that program, in the same folder shape. This is what we actually read, because LabVIEW files are drawings, not text.

the new program

UNMScope_Python\

Everything we write. The rest of this talk is inside this one folder.

The five files at the top

Where the project explains itself

README.mdThe front door. What this project is and how to install it. Read first, once.
ROADMAP.mdThe living plan. Which features are finished, which are half-done, and a list of open questions waiting on a decision or a measurement. The most useful file in the repository.
CLAUDE.mdThe house rules — for example "never state a size from looking at a screenshot, measure it", and "controls that do nothing must look disabled". Rules we kept breaking until we wrote them down.
COMMANDS.mdA cheat sheet of the exact commands to run the program, the tests, and the comparison tools. So nobody has to remember them.
pyproject.tomlA packing list. It names the outside pieces this program needs — the window toolkit, the camera library, the card library — so one command installs all of them.

Conventions

What a name tells you before you open it

louisxiv_waveform.pyThe louisxiv_ prefix means: this is a direct translation of the old program's own calculation. Change it only if LouisXIV changed.
fake_fpga.pyfake_ and Simulated mark the stand-in versions used when no hardware is attached.
test_roi.pyAnything starting test_ is a check, not part of the program. It exists to prove roi.py is right.
_display_frame()A leading underscore means internal — used only inside its own file. Without one, it is meant to be used from elsewhere.
29c_trigger_up...pyA leading number means a hardware experiment, kept in the order it was run, like numbered pages in a lab notebook.

How the pieces connect

Follow one action down

Pressing Acquire walks straight down the drawers. Each file uses the one below it and knows nothing about the one above.

gui\main_window.pyreads the boxes on screen — exposure, range, how many planes
↓ asks for a movement plan
hardware\louisxiv_waveform.pyworks out the sweep, exactly as the old program does
↓ needs to turn microns into volts
config\calibration.pysupplies this rig's calibration numbers
↓ hands the finished plan over
hardware\fpga_trigger.pyloads it onto the card and starts it
↓ images come back
fileio\tiff_stack.pywrites the stack in the old program's format and naming

tests\

A mirror of the program

src\unmscope\              tests\
  hardware\roi.py      →    test_roi.py
  hardware\stage.py    →    test_stage.py
  gui\camera_tab.py    →    test_camera_tab.py
  fileio\tiff_stack.py →    test_tiff_stack.py
  analysis\...         →    test_projections.py

  28 files · 246 checks · about 35 seconds

For nearly every file in the program there is a matching file of checks, named the same way with test_ in front. If you change roi.py, you look at test_roi.py.

A check is simply: set up a known situation, do the thing, state what the answer must be. If the answer changes, the check fails and says so.

They all run without a microscope, in half a minute, and they run before every save of the work. That is the safety net that makes it reasonable to keep changing this software.

spikes\ and tools\

The two folders that are not the program

spikes\ — 38 numbered scripts

Each one answers a single question about the real hardware: does this pin actually output five volts? is the trigger really 100 milliseconds? They are numbered in the order they were run and kept forever, like a lab notebook.

They are not part of the program and never run automatically. Their value is as evidence — when someone asks "how do we know the laser channel is on that pin", the answer is a numbered script and the measurement it produced.

tools\ — 3 utilities for us

A live panel for poking at the card by hand, a monitor for the signal stream, and a script that screenshots both the old and new programs and prints how many pixels apart their layouts are.

Useful while building the software. Never seen by whoever is using the microscope.

docs\

Why a fact is a fact

Fourteen notes recording what was measured, as opposed to what was assumed. Each one names the part of the old program it came from and the date it was checked on the instrument.

This exists because six months later nobody remembers why a number is 6600 rather than zero — and guessing again is how mistakes get reintroduced.

Typical entries

fpga_io_map.md — which physical connector each signal comes out of, verified with a meter.

known_issues.md — traps we have already fallen into, so nobody falls in twice.

camera_tab.md — for one panel: what each control does, which LabVIEW page it came from, and a table of how far off our layout is in pixels.

While it is running

Where settings actually live

This trips people up, so it is worth being explicit. There are two settings files, and only one of them is ours.

The old program's settings file is read-only input. On first run we copy it, exactly, into a folder belonging to the user. From then on the new program reads and edits only its own copy.

That way you can change something in the new program without any risk of disturbing the software the lab depends on today.

Read, never written

UNMScope_Source\...\SPIMProject.ini — LouisXIV's own settings, including this rig's calibrations.

Ours to change

~\.unmscope\SPIMProject.ini — a copy made on first run, in your user folder. Every setting the new program saves goes here.

Practical

"I want to change something — where do I look?"

a button or a layoutThe matching file in gui\. Panels are one file each, named after the panel.
how the mirrors movehardware\louisxiv_waveform.py — but check the old program first, since it is a translation.
a calibration numberconfig\, and normally through the calibration window rather than by editing code.
file names or formatfileio\tiff_stack.py.
"is this already known?"ROADMAP.md for open questions, docs\known_issues.md for traps.
"how do I run it?"COMMANDS.md.

To take away

Four things about the structure

  • The folders are the filing system. Five drawers in the program, plus separate folders for checks, hardware experiments, utilities and written records.
  • Dependencies only point downward. The window may use the hardware code; the hardware code knows nothing about the window. That is why either can be worked on alone.
  • Names are literal, and they carry meaning. test_, fake_, louisxiv_ and a leading underscore each tell you what a file or function is for before you open it.
  • Every file says where it came from. The note at the top of each one names the page of the old program it was translated from — which is what makes the translation checkable rather than trusted.
